# 最小 pilot 与正式定题

## 选什么实验

先问“哪项假设不成立会让当前主张失去意义”。选择最小但有判别力的实验，预先给出一个足够强的简单对照、相同的信息条件和与问题匹配的资源预算。目的可以是支持、区分或否定机制，不要求每个 pilot 都得到正结果。

示例：若方法主张记忆帮助选择专家，先检验真实专家是否有互补错误，再在同工具、同标签和同调用预算下比较简单路由与拟议记忆。工具接口返回成功或合成 fixture 的分数，只能支持接口流程，不是情感任务效果。

使用 [pilot 模板](../assets/pilot.md) 的计划部分生成带版本和 run ID 的文件，例如 `v002_pilot_01_plan.md`。不确定的数据可用性、指标、运行预算写成待解决问题，不填写虚构的默认数值。已授权、资源明确且可以执行的 pilot 应完成执行；关键资源缺失时明确所缺事实，继续不依赖它的工作，不把计划当作完成。

## 执行前固定什么

- 对应 idea 版本、哈希、pilot/run ID 和最危险假设；如果要测的是旧版，明确它对新版的适用范围。
- 输入、数据划分/来源和信息权限；避免用同一批答案持续改想法又声称独立验证。
- 方法、强简单对照、指标、资源上限及停止条件；结果出来后不要悄悄改判据。
- 哪种观察支持继续、需要修改、意味着停止；避免以“总有一项涨了”代替预定目标。
- 实际脚本/配置/依赖/权重版本和输出路径；优先在现有工程中用独立 pilot 目录，不在论文库放运行脚本。

这是一张有时间记录的本地实验计划，不要求正式预注册、申请外部服务或建立数据库。

## 执行与记录

按当前用户授权执行，复用现有环境。不要因 skill 的终点包括 pilot 就自行启动长训练、付费调用或占用未分配资源。明确授权过的本地实验无需每步再问。

保存可复查的命令、配置、原始输出、错误、成本/耗时及未完成项。对比方法使用相同合理条件；模型权重训练、memory 构建和候选搜索获得的标签反馈应分别说明。区分探索数据与最终保留数据，避免反复查看 test 后仍把它称作独立测试。

保留执行时的计划，不在看到结果后覆盖它。使用模板的结果部分生成与计划同 ID 的 `v002_pilot_01_result.md`；后续运行递增编号。结果记录原计划路径/哈希和实际运行标识。固定名称的文件如需使用，仅作指向历史 run 的索引。结果包括：

1. 实际运行了什么、运行条件与版本、日志和原始结果在哪里。
2. 方法和对照的可比较结果；没有的量写“未测量”，不写零。
3. 对关键假设支持、反对或仍无法区分的证据，以及不确定性。
4. 是否偏离计划、结果只适用于什么范围、哪些实验仍没跑。

运行失败可记录为失败；它不等于机制被否定。差异落在噪声范围、数据权限有泄露或对照不公平时，应解释结果不足以判断，而不是自动升级状态。

## 何时能交接

正式定题应同时有：

- 适用于当前研究问题的实际 pilot；代码 smoke test、合成闭环和计划文档不足以证明目标机制。
- 可复查的结果与强简单对照；剩余不确定性明确，结论没有越过证据。
- 研究者在看过结果后的实际决定，记录继续、修改或停止的理由；缺少决定时停在“已有 pilot，待人的取舍”。

用户若明确选择在混合或负面结果下继续探索，也可以交接，但应写明这是一项有风险的研究投入决定，不能把它改写成“pilot 已支持核心假设”。已被数据否定的主张仍应修正或撤回。

复用较早版本的 pilot 时，逐项说明新旧变化及原结果对当前主张、数据、方法和指标的适用关系。只改标题/措辞时无需重跑；改变了被测机制或实验条件时补充相应验证。不能刷新旧 run 的哈希，把它写成测试过新版本。

按 [handoff 模板](../assets/handoff.md) 留下简短材料，使用如 `v002_handoff_01.md` 的不覆盖文件名：确定的问题、最接近工作与实际差异、当前版本、pilot 证据与适用关系、局限、后续实验、资源和工程路径、人的决定出处。进入工程后新结果仍可把 idea 退回修改。不要自动声称论文已具备投稿效果，也不要为了交接擅自创建完整稿件。

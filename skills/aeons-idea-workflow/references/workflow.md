# 运行约定

## 首先定位实际进度

按当前请求定位项目根目录与目标 idea，不通过当前脚本目录推断项目位置。先读 `AGENTS.md` 和现有说明；从 idea、review、决策和实测产物交叉判断进度。文件存在只表示有文件，不能推出“人已读”“人已采纳”或“实验成功”。

新项目默认 `brainstorming/paper/`。旧项目有 `brainstorming/papers/` 时继续使用，避免两份文献库。原稿在 `my_idea/`、旧评审在专题目录时，读取即可；确需纳入新结构时保留原文并记录来源，批量迁移应来自用户要求。

## 版本与评审对应

- idea ID 用稳定、简单的目录名，例如 `001-affect-harness`。论文标题可以变，ID 不变。
- `v001.md` 保留原始表达；后续版本保留变化与其理由。零散原文无需先填长模板。
- 日常编辑使用 `draft.md` 或用户原稿；`vNNN.md` 是冻结快照。若手动改了旧快照，先另存当前改动，再从可核实备份恢复旧快照；无法恢复时如实说明历史偏离，不修改旧哈希伪装历史未变。helper 无法自动重建丢失的旧内容。
- helper 的 `versions.json` 仅记录文件、SHA256、来源、理由与 UTC 时间；不表示用户批准。
- review 开头记录被评文件的相对路径与实际 SHA256，可用标准库 `hashlib` 计算。
- 一个版本有多轮评审时使用 `v002_review_02.md` 等不覆盖的文件名；不重写历史评论让它显得早就知道新结果。
- 文件被手动修改后，当前内容与旧哈希不符。提示这是对旧内容的评审，保存新版本再继续；已有内容和旧哈希都应保留。
- 分支方向使用新 ID，并注明从哪版分出。不同假说不要仅凭题目相近强行合并。

## 文献库与阅读

论文 PDF、MD 及图片共用库；研究解释写在 `idea_review/<id>/`，不要改转换后的原论文 MD 来夹带 AI 结论。metadata 可记录：题名、作者、正式出处/首发年份、DOI/原始链接、版本、下载位置、哈希、转换方式、读取范围与缺失项。

全文获取失败就保留原始链接与原因，向用户提供待补清单；不要生成假 PDF。只读摘要时局限在摘要支持的层面，不编造方法细节或实验数字。引用原段落定位时使用章节/表/页码，注意 PDF 页码与论文印刷页码可能不同。

优先阅读能改变选择的少量核心近邻，再决定是否扩查。没有检索到重合工作只能说明当前检索未发现，不能证明首创。新增直接近邻时更新相关比较，而不是把所有阅读笔记重写一遍。

## 发散、收敛与增量 review

发散阶段保留不成熟的观察与反直觉想法，可以让用户解释灵感或提出替代机制。收敛阶段才聚焦一个可检验问题，核查最近邻、简单解释、可用数据和资源。

初次 review 建立证据与问题框架；后续 review 说明“本轮输入变化 → 哪些判断变了 → 哪些风险还在 → 最有价值的下一步”。如果新版本只改名称或措辞，可以简短说明其不改变先前实质判断，不制造一份更长的审稿报告。

复杂问题可委派独立检索或反方审查，再由主 agent 核对证据。不要把多个 agent 的相同意见当独立实验或多数票证明。没有必要让每个小想法都经历全套角色辩论。

## 人的决策记录

`decisions.md` 每轮几行即可：

```text
对象：001-topic / v002
依据：v002_review.md；关键论文 §3；或 v002_pilot_01_result.md
人的决定：采纳A，保留B，暂缓C
理由：用户实际表达的理由；未表达则写未说明
出处：当前用户消息/用户编辑的文件及日期
下轮问题：最需要解决的一个不确定点
```

AI 可给出建议，但只有实际用户表达支持时才能写“人的决定”。用户没有逐条表态不妨碍检索或整理，不应替其补造理由或把默认选项当批准。已经明确授权的修改可直接完成；暂缓的研究建议也不等于暂停其他工作。

## 恢复与交接

恢复时说明目标版本、上一轮人的取舍、已有证据和最需要的新输入，再推进。输入变化不大时复用已有材料，避免重新搭一遍流程。

pilot 开始前和结果出来后读 [pilot-and-handoff.md](pilot-and-handoff.md)。实际结果若否定关键假设，应回到 idea 修改或停止，不用更乐观的文字绕过结果。原本的“值得验证”并不绑定后续研究投入。
